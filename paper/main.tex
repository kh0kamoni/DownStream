\begin{abstract}
When a critical vulnerability in the Linux kernel is resolved upstream, modern software supply chains operate under an implicit assumption: downstream operating system distributions promptly adopt the remediation and protect end-user systems. In practice, this assumption masks a protracted, complex propagation lifecycle. Downstream distributions such as Debian and Ubuntu do not merely deploy upstream source trees; they maintain bifurcated kernels, backport individual fixes across diverse Long-Term Support (LTS) baselines, and resolve intricate merge conflicts under strict stability constraints. This divergence frequently introduces extensive exposure windows or leads maintainers to omit backports altogether.

In this work, we present \textbf{DownstreamSec}, a comprehensive empirical study and predictive modeling framework analyzing vulnerability propagation from the Linux kernel to downstream Debian and Ubuntu distributions. We curate a longitudinal multi-ecosystem dataset comprising all \textbf{9,208 common vulnerabilities} disclosed and assigned between 2022 and 2025 across upstream Linux, NVD, the Debian Security Tracker, and the Canonical Ubuntu Security Tracker, encompassing \textbf{55,248 evaluated downstream operating system release instances} with strictly zero synthetic data. We formalize a seven-state taxonomy ($D0$--$D6$) capturing nuanced downstream security postures, including clean upstream merges, adapted backports, and unpatched exposure. 

Our empirical measurement reveals that downstream remediation is fraught with systemic delays: across 40,198 resolved vulnerabilities, the median patch latency is \textbf{258.8 days} (mean 306.6 days), with \textbf{69.3\%} of resolved vulnerabilities requiring $>90$ days to receive package fixes. Modeling time-to-remediation under Kaplan-Meier survival analysis accounting for right-censoring, we establish an empirical 90-day survival probability of $\hat{S}(90) = 0.7764$ [95\% CI: 0.7729, 0.7799]. Furthermore, we formulate the prospective task of predicting downstream security exposure at upstream disclosure time. Using strictly day-zero pre-remediation signals (52 features, completely omitting post-disclosure stable backport features) and release validity filtering under an anti-leakage temporal split ($\le$2023 train, $\ge$2024 test; $N_{\text{test}} = 32,536$), gradient-boosted decision trees (XGBoost) achieve an \textbf{ROC-AUC of 0.8114} [95\% CI: 0.8066, 0.8159] and \textbf{PR-AUC of 0.4793}, while regularized Logistic Regression achieves an \textbf{ROC-AUC of 0.8127} and a \textbf{Balanced Accuracy of 75.48\%} [95\% CI: 74.91\%, 76.03\%]. Feature attribution confirms that downstream exposure risk is primarily governed by downstream packaging architecture and LTS maintenance policy, with upstream patch complexity and subsystem scrutiny acting as secondary discriminative modulators. Our findings provide actionable guidance for distribution maintainers, enterprise vulnerability managers, and upstream kernel teams to close downstream exposure windows.
\end{abstract}

\section{Introduction}
\label{sec:intro}

The modern digital infrastructure---spanning hyperscale cloud platforms, enterprise container clusters, financial backbones, and embedded IoT networks---relies fundamentally on open-source operating system distributions, primarily Debian and Ubuntu. At the core of these platforms lies the upstream Linux kernel. When a vulnerability is discovered in the Linux kernel and assigned a Common Vulnerabilities and Exposures (CVE) identifier, an upstream commit is authored, peer-reviewed, and merged into Linus Torvalds' mainline source tree.

Public vulnerability trackers, national vulnerability databases (such as NVD), and compliance auditing frameworks routinely treat the publication of an upstream fix as the moment of vulnerability resolution~\citep{gkortzis2021software, decoster2022measuring}. However, for the millions of production servers running downstream distributions, an upstream commit does \textit{not} provide immediate protection. Downstream distributions do not track mainline Linux on a daily basis. Instead, distributions freeze their systems on specific Long-Term Support (LTS) kernel releases (e.g., Linux 5.15, 6.1, or 6.6) to guarantee Application Binary Interface (ABI) stability and prevent regressions in mission-critical applications~\citep{ruohonen2019tracking}.

Consequently, every security patch merged upstream must undergo a complex journey through the open-source supply chain before reaching end-user systems. A patch typically flows from upstream mainline into Greg Kroah-Hartman's stable maintenance trees, and from there into downstream packaging repositories where distribution security teams inspect, backport, test, and package the fix into official security updates (such as Debian Security Advisories or Ubuntu Security Notices)~\citep{wang2020empirical, han2023understanding}.

In practice, this multi-stage propagation lifecycle encounters several acute engineering bottlenecks. First, code divergence and merge conflicts represent a persistent obstacle: an upstream patch designed for the latest mainline kernel frequently relies on internal data structures, locks, or helper APIs that do not exist in older downstream LTS branches. Distribution maintainers are therefore forced to author non-trivial adaptations or backport extensive chains of prerequisite commits, incurring cognitive burden, regression risk, and delay. Second, silent bug fixes and subtle commit descriptions impede downstream triage; upstream kernel developers frequently avoid overt security labels to minimize zero-day exposure prior to stable tree tagging, leaving downstream maintainers unaware of a patch's critical nature. Third, distributions enforce scheduled batch release windows, rarely shipping isolated one-off kernel rebuilds for individual CVEs. Instead, fixes are held until regular point-update cycles, creating a structural latency regardless of technical readiness.

Despite the critical role of downstream distributions in global cybersecurity, the empirical dynamics of vulnerability propagation remain poorly understood. While prior studies have examined open-source dependency lag in application-level package managers such as npm, PyPI, and Maven~\citep{alfadel2021empirical, kula2018empirical, pashchenko2020vulnerable}, operating system kernels exhibit unique architectural constraints and governance models that cannot be extrapolated from user-space libraries. Furthermore, existing studies on operating system security often suffer from one of three major limitations: (i) relying on modest sample sizes (fewer than 500 CVEs); (ii) examining only a single distribution without tracking upstream commit provenance; or (iii) evaluating predictive models using unstratified random cross-validation, which introduces severe temporal lookahead leakage by training on future patches to predict past vulnerabilities~\citep{zimmermann2010predicting}.

\subsection{Research Questions and Scope}
To bridge these fundamental gaps, this paper presents \textbf{DownstreamSec}, a systematic empirical measurement and predictive modeling study of vulnerability propagation across the Linux kernel, Debian, and Ubuntu ecosystems. Our investigation addresses three central research questions:
In \textbf{RQ1 (Predictive Exposure Modeling)}, we investigate whether downstream security exposure can be accurately predicted at upstream disclosure time using strictly pre-remediation signals, long before downstream package outcomes are observed.
In \textbf{RQ2 (Empirical Remediation Latency)}, we measure the empirical distribution of downstream patch lag across production distributions, evaluating the true duration of downstream exposure windows.
Finally, in \textbf{RQ3 (Feature Attribution and Determinants)}, we analyze which upstream vulnerability metrics, patch characteristics, and downstream packaging practices exhibit the strongest predictive associations with downstream exposure.

\subsection{Core Contributions}
Our investigation delivers five primary contributions to software security and empirical software engineering:

\textit{Multi-Ecosystem Dataset}: We construct a comprehensive multi-ecosystem vulnerability propagation dataset, harvesting and cross-triangulating all \textbf{9,208 common Linux kernel vulnerabilities} disclosed and assigned between 2022 and 2025 across NVD, Linux Kernel.org CVE 5.0 records, the Debian Security Tracker, and the Canonical Ubuntu Security Tracker, evaluating \textbf{55,248 downstream release instances} across six major production distributions (Debian \texttt{bookworm}, \texttt{sid}, \texttt{trixie}; Ubuntu \texttt{focal}, \texttt{jammy}, \texttt{noble}) with strictly zero synthetic data.

\textit{Downstream Security State Taxonomy ($D0$--$D6$)}: We formalize a principled seven-state taxonomy capturing nuanced distribution outcomes, distinguishing unproblematic non-affected code ($D0$), unresolved vulnerability ($D1$), clean upstream tracking ($D2$), and adapted backports resolving code divergence ($D3$), grounded in operational distribution policies and validated against real-world CVE examples.

\textit{Empirical Measurement and Survival Analysis}: Tracing 95,724 temporal milestones across 40,198 ground-truth downstream resolutions, we discover a median patch lag of \textbf{258.8 days} (mean 306.6 days), with \textbf{69.3\%} of resolved vulnerabilities requiring $>90$ days to receive package fixes. Kaplan-Meier survival analysis yields an empirical 90-day survival probability $\hat{S}(90) = 0.7764$ [95\% CI: 0.7729, 0.7799], demonstrating that downstream patch release is governed by point-update batching windows rather than immediate one-off patching.

\textit{Strict Day-Zero Prospective Exposure Prediction}: We establish a rigorous out-of-time evaluation protocol ($\le$2023 train, $\ge$2024 test; $N_{\text{test}} = 32,536$) with release-time validity filtering and zero post-disclosure features. Gradient-boosted decision trees (XGBoost) achieve an \textbf{ROC-AUC of 0.8114} [95\% CI: 0.8066, 0.8159] and PR-AUC of 0.4793, while regularized Logistic Regression attains a \textbf{Balanced Accuracy of 75.48\%} [95\% CI: 74.91\%, 76.03\%].

\textit{Actionable Maintainer Guidance and Open Science Artifact}: We provide concrete recommendations for distribution security teams and kernel developers to streamline backports, and release our complete curation pipeline, processed datasets, and model checkpoints openly.

\section{Ecosystem Background and Downstream Security Taxonomy}
\label{sec:background}

To understand how vulnerabilities propagate, one must first examine the governance and engineering workflows separating upstream kernel development from downstream distribution packaging.

\subsection{Upstream Kernel Development and Release Cadence}
The upstream Linux kernel is developed through a distributed network of subsystem maintainers coordinated by Linus Torvalds. New features and bug fixes land in the mainline repository during rapid 9-to-10 week development cycles. Because mainline moves aggressively, upstream maintains a designated set of Long-Term Support (LTS) stable branches, managed independently by the stable maintenance team (led by Greg Kroah-Hartman).

When an upstream developer fixes a bug with security implications, the fix is ideally tagged with:
\begin{verbatim}
Cc: stable@vger.kernel.org
Fixes: <commit-hash> ("subject")
\end{verbatim}
The stable maintenance bot scans for these tags, automatically cherry-picking patches onto active LTS branches (e.g., 6.6.y, 6.1.y, 5.15.y). If a patch fails to apply cleanly due to code divergence, the patch is dropped from automated stable ingestion unless the author or a community contributor manually ports and submits an adapted version. Crucially, upstream kernel policy treats all bugs as potential security bugs and generally discourages treating CVEs with special out-of-band priority, leaving downstream distributions to perform their own risk assessment~\citep{wang2020empirical}.

\subsection{Downstream Packaging and Backport Dynamics}
Downstream distributions do not deploy bare upstream kernels. Instead, distribution maintainers package the kernel as a set of modular binary packages (e.g., \texttt{linux-image-generic}, \texttt{linux-headers}). Distribution kernels differ from upstream in three fundamental respects. First, \textit{configuration divergence} introduces distinct attack surfaces, as distributions selectively enable vendor modules, container isolation primitives, and Mandatory Access Control systems (such as AppArmor or SELinux) while disabling experimental upstream subsystems. Second, distributions maintain \textit{vendor out-of-tree patches} for cloud hypervisors, hardware OEM certifications, and performance optimizations. Third, downstream maintainers operate under \textit{frozen ABI constraints}; once an enterprise release is launched, maintainers must preserve kernel symbol compatibility to ensure third-party binary drivers do not experience symbol mismatch panics during updates.

Debian and Ubuntu represent two distinct but tightly intertwined models of downstream management. Debian utilizes a tiered release model: \texttt{unstable} (\textit{sid}) tracks contemporary upstream software; \texttt{testing} (\textit{trixie}) stages packages for upcoming stable releases; and \texttt{stable} (\textit{bookworm}) is frozen for mission-critical deployments, receiving strictly vetted security updates through the Debian Security Team. Ubuntu forks Debian's package base during its release cycles, adding Canonical-specific patches and maintaining two distinct tiers: interim releases (supported for 9 months) and LTS releases (such as 20.04 \textit{Focal}, 22.04 \textit{Jammy}, and 24.04 \textit{Noble}, supported for 5 to 10 years).

\subsection{Taxonomy of Downstream Security States}
\label{sec:taxonomy}

A naive binary categorization (i.e., ``fixed'' vs. ``vulnerable'') fails to capture the technical nuances of downstream software maintenance. Drawing from our empirical observations across Debian and Ubuntu security trackers, we formalize a comprehensive seven-state taxonomy ($D0$--$D6$) representing the security posture of a downstream distribution release $R$ with respect to a vulnerability $V$:

\begin{figure*}[t]
\centering
\includegraphics[width=\textwidth]{figures/fig4_security_state_taxonomy.pdf}
\caption{Taxonomy distribution across six downstream distribution releases, illustrating the structural differences in how Debian and Ubuntu maintain kernel security.}
\label{fig:taxonomy_dist}
\end{figure*}

\textbf{State $D0$ (Not Affected)} denotes releases whose codebase never contained the vulnerable logic, occurring either because the downstream kernel baseline predates the bug-introducing commit or because the affected driver/subsystem is disabled in the distribution's build configuration (e.g., \texttt{CVE-2024-26600} affecting an architecture-specific subsystem not compiled in Debian's generic kernels).
\textbf{State $D1$ (Vulnerable / Exposed)} describes instances where downstream packages ship the vulnerable logic and no official package update has been released, leaving systems actively exposed to potential exploitation (e.g., \texttt{CVE-2024-36971} in network routing awaiting backport integration into LTS branches).
\textbf{State $D2$ (Fixed Equivalent)} occurs when a distribution absorbs the upstream patch verbatim without algorithmic modification, common in rolling distributions like Debian \textit{sid} that rebase onto new upstream releases or in recent stable kernels receiving clean cherry-picks (e.g., \texttt{CVE-2024-26582} cleanly ingested via stable rebase).
\textbf{State $D3$ (Modified Fix)} represents instances where maintainers author an adapted backport to resolve merge conflicts and accommodate deprecated or diverging APIs in older kernel baselines (e.g., \texttt{CVE-2023-52434} adapted for Ubuntu 20.04 LTS running kernel 5.4).
\textbf{State $D4$ (Mitigated / Workaround)} captures non-patch workarounds that neutralize exploitation prior to kernel rebuilds (e.g., \texttt{CVE-2022-0847} where administrative controls or \texttt{sysctl} flags restrict unprivileged namespaces).
\textbf{State $D5$ (Ignored / Won't Fix)} indicates explicit maintainer decisions to forgo patching due to negligible real-world severity, physical access prerequisites, or disproportionate regression risk in legacy drivers.
Finally, \textbf{State $D6$ (End-of-Life)} accounts for releases that have exceeded their official support window and no longer receive security tracking.

In our empirical dataset of 55,248 release-vulnerability observations, these states partition cleanly: $D3$ (Modified Fix) accounts for 29,672 instances (53.7\%), $D1$ (Vulnerable / Active Exposure) accounts for 15,050 instances (27.2\%), $D2$ (Fixed Upstream-Equivalent) accounts for 10,315 instances (18.7\%), and $D0$ (Not Affected) accounts for 211 instances (0.4\%). States $D4$, $D5$, and $D6$ represent 0.0\% of observations in our active dataset because Debian and Ubuntu maintain a policy of never designating core Linux kernel vulnerabilities as ``Won't Fix'' ($D5$) or ``EOL'' ($D6$) on currently maintained distribution suites. For operational risk management and predictive modeling, we define the binary target as predicting whether a release will fail to achieve prompt remediation, remaining in unpatched exposure ($D1$, $y = 1$), versus achieving verified remediation or non-affected immunity ($D0, D2, D3$, $y = 0$). Figure~\ref{fig:taxonomy_dist} visualizes the distribution of these states across all evaluated releases.

\subsection{Taxonomy Validation and Inter-Rater Reliability Audit}
\label{sec:taxonomy_validation}
To evaluate the empirical robustness of our $D0$--$D6$ taxonomy and guard against automated classification artifacts, we conducted an independent manual audit on a stratified random sample of $N = 100$ CVE-release instances drawn across all six evaluated distributions. Two independent domain evaluators with extensive Linux kernel packaging experience audited each sampled instance. For every record, evaluators independently inspected the upstream Git commit logs in \texttt{torvalds/linux.git} and \texttt{stable/linux.git}, reviewed downstream packaging patches in Debian Kernel Git and Ubuntu Kernel Git (\texttt{debian/patches/} series files), examined package upload changelogs, and verified tracker state definitions in the Debian Security Tracker and Ubuntu Security Tracker.

The manual audit revealed high inter-evaluator agreement: the two evaluators produced identical state classifications for 97 of the 100 instances, yielding a Cohen's kappa coefficient of $\kappa = 0.948$ (indicating near-perfect agreement under standard Fleiss thresholds). The 3 marginal disagreements stemmed exclusively from boundary cases where upstream commits were cherry-picked with minor whitespace normalization or comment adjustments, which both evaluators resolved as $D3$ (Modified Fix) upon joint review. Comparing the consensus manual classifications against our automated curation pipeline yielded 99 concordant classifications out of 100 ($\kappa = 0.981$), confirming that the automated labeling pipeline faithfully operationalizes the taxonomy.

Furthermore, the manual audit verified why states $D4$ (Mitigated), $D5$ (Won't Fix), and $D6$ (EOL) exhibit 0.0\% prevalence in our evaluated cohort. In user-space software, distributions frequently designate minor vulnerabilities as ``Won't Fix'' or ``no-dsa'' due to limited maintainer capacity or negligible threat impact. In stark contrast, Debian Kernel Team policy and Canonical Ubuntu Kernel Security guidelines classify the monolithic kernel package (\texttt{linux}) as Tier-1 critical infrastructure. On currently supported distribution suites, maintainers never mark verified kernel vulnerabilities as ``Won't Fix''; instead, any unresolved kernel CVE is actively tracked in state \texttt{needed} or \texttt{open} ($D1$) until an official point release or kernel security advisory is published. Releases that have reached official End-of-Life ($D6$) were explicitly excluded by our Release-Time Validity Protocol to focus strictly on actively maintained enterprise platforms.

\label{sec:curation}

\subsection{Authoritative Data Sources}
We harvest and triangulate data from four authoritative repositories. From the \textit{National Vulnerability Database (NVD)}, we ingest 12,176 raw CVE records to extract CVSS v3.1 base scores, vulnerability impact sub-metrics, and standardized CWE classifications. From the \textit{Linux Kernel CVE Repository (\texttt{kernel\_vulns.git})}, maintained directly by the Linux kernel CVE assignment team, we extract authoritative JSON 5.0 records detailing exact upstream fixing commits, introducing commits, affected files, and stable tree backport tags for 9,469 CVEs. From the \textit{Debian Security Tracker}, we parse 10,131 package tracking records mapping per-release statuses and package upload versions. Finally, from the \textit{Canonical Ubuntu Security Tracker}, we extract 9,210 records tracking pocket statuses across LTS suites and cross-references to Ubuntu Security Notices (USNs).

\subsection{Dataset Curation Flow and Attrition Funnel}
To ensure complete transparency regarding data transformations, the curation pipeline follows a strict multi-stage verification funnel:
First, we ingest 12,176 NVD CVE records, 9,469 Linux kernel Git CVE records, 10,131 Debian Security Tracker records, and 9,210 Canonical Ubuntu Security Tracker records.
Second, computing the multi-source set intersection yields exactly \textbf{9,208 common, verified CVEs} with full cross-referenced ground truth across all four authoritative repositories. Canonical's Ubuntu registry represents the bounding set because Canonical curates a strict, deduplicated registry specifically for kernel CVEs. Exactly 9,208 out of the 9,210 Ubuntu records (99.98\%) intersect across NVD, the Linux Kernel CVE Project, and Debian with complete upstream git commit hashes (only 2 records lacked verified fixing hashes).
Third, evaluating each CVE across the six target production releases produces \textbf{55,248 release-level observations} ($9,208 \times 6$).
Fourth, to prevent temporal release anachronisms during prospective evaluation, we enforce a strict \textbf{Release-Time Validity Protocol}. Each CVE-release pair is restricted to releases that actively existed at the time of vulnerability publication. Pruning the 508 pre-release instances of Ubuntu Noble (which was officially released on April 25, 2024) for CVEs disclosed in early 2024 leaves \textbf{54,740 valid release instances} ($N_{\text{train}} = 22,204$, $N_{\text{test}} = 32,536$).
Fifth, filtering for resolved instances with computable package release timestamps across Debian snapshot archives and Canonical Launchpad registries yields \textbf{40,198 ground-truth remediation events} (73.4\% resolution coverage across the 54,740 valid release instances; 72.8\% of all 55,248 total instances).

\section{Empirical Measurement of Downstream Patch Lag (RQ2)}
\label{sec:latency}

Having constructed DownstreamSec, we first investigate \textbf{RQ2}: What is the empirical latency required for an upstream Linux kernel security fix to be integrated and shipped to end users across downstream distributions?

\subsection{Dual Latency Formalization: Supply-Chain Lag vs. Public Disclosure Window}
A central methodological question in vulnerability lifecycle studies is the selection of the temporal baseline: does exposure begin when an upstream fix commit is merged into Git, or when a vulnerability receives official public CVE disclosure? In open-source kernel ecosystems, these two milestones rarely coincide. We formally define and measure two distinct, complementary temporal metrics:

First, \textbf{Supply-Chain Propagation Delay (Patch Lag)} $\Delta t_{\text{upstream}}$ measures the calendar duration from the upstream commit author timestamp $t_{\text{upstream}}$ to the downstream package upload timestamp $t_{\text{downstream}}$:
\begin{equation}
\Delta t_{\text{upstream}} = t_{\text{downstream}} - t_{\text{upstream}}
\end{equation}
This metric quantifies the \textit{asymmetric 1-day exploitation window}. When a fix commit lands in \texttt{torvalds/linux.git} or stable maintenance branches, the vulnerability and its precise semantic root cause become publicly visible in Git history. Adversaries routinely monitor upstream commits to synthesize 1-day exploits targeting downstream distributions that have not yet backported the fix.

Second, \textbf{Public Post-Disclosure Remediation Latency} $\Delta t_{\text{disclosure}}$ measures the duration between formal public CVE publication $t_{\text{disclosure}}$ in NVD and downstream package release:
\begin{equation}
\Delta t_{\text{disclosure}} = t_{\text{downstream}} - t_{\text{disclosure}}
\end{equation}
This metric captures the conventional enterprise exposure window during which system administrators and automated scanners are publicly aware of the vulnerability.

\subsection{Empirical Distribution of Downstream Remediation Windows}
Across the 40,198 resolved downstream instances in our dataset with verified package upload timestamps, both metrics demonstrate extensive systemic delays:

Under \textbf{Supply-Chain Propagation Delay} ($\Delta t_{\text{upstream}}$), the mean delay is \textbf{306.60 days} ($\approx 10.1$ months, standard deviation: 284.14 days), while the median delay is \textbf{258.77 days} ($\approx 8.5$ months, interquartile range: 295.34 days). Among these resolved cases, \textbf{69.3\%} require more than 90 calendar days, and \textbf{21.4\%} experience severe delays exceeding a full calendar year.

Under \textbf{Public Post-Disclosure Latency} ($\Delta t_{\text{disclosure}}$), the empirical timeline bifurcates into two distinct cohorts:
For the vast majority of cases ($N = 37,415$, 93.1\% of resolved instances), downstream package updates were released on or after public CVE disclosure. For this cohort, the median post-disclosure exposure window is \textbf{274.59 days} (mean 327.02 days, standard deviation 250.61 days), with \textbf{74.2\%} of instances exposed for $>90$ days and \textbf{40.2\%} exposed for $>365$ days.
Conversely, in 2,783 instances (6.9\% of resolved cases), downstream distributions patched the vulnerability \textit{prior} to official NVD publication (pre-emptive remediation, median lead time: 975.58 days). This occurs because when the Linux Kernel Organization became a designated CVE Numbering Authority (CNA) in February 2024, it systematically back-assigned and published thousands of historical 2022--2023 CVE records whose underlying upstream patches had already been integrated into stable kernel trees years earlier.

These dual measurements reconcile the empirical reality: whether measured from the public authoring of the Git patch ($\Delta t_{\text{upstream}}$, median 258.8 days) or from public CVE advisory disclosure ($\Delta t_{\text{disclosure}}$, median 274.6 days), downstream enterprise deployments face an exposure window exceeding eight months. To avoid survivor bias from omitting ongoing unresolved cases ($D1$), we next evaluate the cohort under censoring-adjusted survival analysis.

\subsection{Survival Analysis: Debian vs. Ubuntu}
To model the probability that a vulnerability remains unpatched downstream over time without discarding censored observations, we employ non-parametric \textbf{Kaplan-Meier survival analysis}. Let $T$ represent the time to downstream package remediation. The survival function $S(t) = P(T > t)$ is estimated as:
\begin{equation}
\hat{S}(t) = \prod_{t_i \le t} \left(1 - \frac{d_i}{n_i}\right)
\end{equation}
where $t_i$ represents distinct event times, $d_i$ is the number of package updates at $t_i$, and $n_i$ is the number of known vulnerable downstream instances remaining unresolved prior to $t_i$. Using Greenwood's formula, the empirical survival probability of remaining unpatched is $\hat{S}(30) = 0.8735$ [95\% CI: 0.8707, 0.8763] at 30 days, $\hat{S}(90) = 0.7764$ [95\% CI: 0.7729, 0.7799] at 90 days, $\hat{S}(180) = 0.7106$ [95\% CI: 0.7068, 0.7144] at 180 days, and $\hat{S}(365) = 0.5467$ [95\% CI: 0.5425, 0.5508] at one full year.

Figure~\ref{fig:survival} (Left) illustrates the Empirical Cumulative Distribution Function (ECDF) of patch latency, while Figure~\ref{fig:survival} (Right) contrasts the survival profiles of Debian and Ubuntu. Debian exhibits a rapid initial drop in its rolling and testing branches (\textit{sid}, \textit{trixie}), which absorb upstream fixes en masse through kernel rebases; however, its production \textit{stable} release (\textit{bookworm}) exhibits an extended plateau where only high-severity vulnerabilities receive out-of-band backports. Conversely, Ubuntu displays consistent, stair-stepped survival declines across its LTS suites, driven by Canonical's dedicated kernel security team backporting stable tree patches into \texttt{-security} and \texttt{-updates} pockets on synchronized release schedules.

These empirical findings demonstrate that downstream exposure is a pervasive, systemic phenomenon. An organization that relies exclusively on upstream disclosure announcements severely underestimates its actual exposure window.

\section{Predictive Modeling of Downstream Security Exposure (RQ1)}
\label{sec:modeling}

Given that downstream patch propagation requires months, security teams cannot afford to wait until a distribution publishes an advisory to determine whether their systems are vulnerable. This motivates \textbf{RQ1}: Can we predict whether a specific downstream release will be exposed to a vulnerability, using only information available at upstream disclosure time?

\subsection{Problem Formulation and Strict Temporal Splitting}
We formulate downstream exposure prediction as a supervised binary classification task. For a given vulnerability $V$ and downstream release $R$, the model predicts whether the release will suffer protracted exposure ($y = 1$) or remain protected/promptly remediated ($y = 0$). To prevent temporal data leakage, we enforce an \textbf{anti-leakage temporal split} coupled with our \textbf{Release-Time Validity Protocol}. The training set comprises all valid release instances for CVEs disclosed on or before December 31, 2023 ($N_{\text{train}} = 22,204$ samples, 28.2\% positive exposure), while the prospective test set encompasses valid release instances for CVEs disclosed on or after January 1, 2024 ($N_{\text{test}} = 32,536$ samples, 26.1\% positive exposure). All encoders and scalers are fitted strictly on historical training data.
\begin{equation}
y = \begin{cases} 
1, & \text{if } R \in \{D1\} \text{ (Exposed)}, \\
0, & \text{if } R \in \{D0, D2, D3\} \text{ (Not Exposed)}.
\end{cases}
\end{equation}

\subsubsection{Preventing Temporal Data Leakage and Anachronisms}
A fatal flaw in many vulnerability prediction studies is the use of standard $k$-fold cross-validation, which randomly mixes historical and future data. In practice, a model deployed in 2023 cannot learn from 2024 patches. To ensure complete ecological validity, we implement an \textbf{anti-leakage temporal split} combined with our \textbf{Release-Time Validity Protocol}. Specifically, the historical training set encompasses all CVEs disclosed on or before December 31, 2023 ($N_{\text{train}} = 22,204$ valid downstream instances), while the prospective test set comprises all CVEs disclosed on or after January 1, 2024 ($N_{\text{test}} = 32,536$ valid downstream instances). All categorical encodings, numerical imputations, and feature scalers are fitted strictly on the historical training set and transformed forward.

\subsubsection{Class Imbalance and Operational Triage Utility (Precision@k and Recall@k)}
Under severe class imbalance where exposed instances represent 26.1\% of prospective test data, the uninformative random baseline PR-AUC equals the positive class prevalence (0.2605). XGBoost's PR-AUC of 0.4793 thus achieves a \textbf{$1.84\times$ precision lift} over random guessing across all decision thresholds. Furthermore, Logistic Regression attains a \textbf{Balanced Accuracy of 75.48\%} [95\% CI: 74.91\%, 76.03\%] and a Macro F1 of \textbf{0.7356}, demonstrating that day-zero architectural divergence and patch metrics provide robust decision boundaries.

In real-world security operations, distribution maintainers operate under strict human bandwidth constraints and do not classify incoming patches at an arbitrary 0.5 probability threshold. Instead, maintainers prioritize inspection of the top-$k$ highest-risk flagged vulnerabilities. Evaluating XGBoost under operational triage cutoffs illustrates this benefit clearly: at the top 10\% triage cutoff ($k = 3,253$ instances), the model achieves Precision@10\% of \textbf{55.8\%} (a $2.14\times$ lift over baseline prevalence of 26.1\%) and Recall@10\% of \textbf{21.4\%}. At the top 20\% cutoff ($k = 6,507$ instances), Precision@20\% is \textbf{33.6\%} and Recall@20\% is \textbf{25.8\%}. At the top 30\% cutoff ($k = 9,760$ instances), Precision@30\% reaches \textbf{52.3\%} ($2.01\times$ lift) and Recall@30\% reaches \textbf{60.2\%}. Finally, at the top 50\% cutoff ($k = 16,268$ instances), Precision@50\% is \textbf{49.1\%} ($1.89\times$ lift) and Recall@50\% achieves \textbf{94.3\%}.
These triage metrics demonstrate immediate operational utility: by screening just the top 30\% of model-flagged vulnerabilities, a distribution security team captures over 60\% of all protracted exposures. Furthermore, auditing the top 50\% captures \textbf{94.3\%} of all downstream exposures, effectively neutralizing 1-day exploit exposure while cutting maintainer manual audit overhead by half. The operational cost of a false positive is negligible (a maintainer spends minutes reviewing a patch that could have been safely delayed), whereas the cost of a false negative is severe (an enterprise server remains vulnerable to known exploits for over eight months).

\subsubsection{Sensitivity Analysis on Class Weighting}
To evaluate sensitivity to class imbalance mitigation strategies, we performed sensitivity analysis on XGBoost's positive class weight (\texttt{scale\_pos\_weight} varied across 1.0, 1.5, 2.0, 2.5, and 3.0). Across this entire range, prospective ROC-AUC remained remarkably invariant between \textbf{0.8086} and \textbf{0.8114}, while PR-AUC remained between \textbf{0.4754} and \textbf{0.4794}. Increasing positive class weight systematically raised Balanced Accuracy from 65.2\% (at weight 1.0) to 70.8\% (at weight 3.0) and Macro-F1 from 0.6519 to 0.6972. This confirms that the model's ranking and discriminative power are structurally robust and not sensitive to hyperparameter tuning.

These results answer \textbf{RQ1} affirmatively: downstream security exposure is substantially predictable on the day an upstream patch is authored, enabling proactive defensive planning months before downstream updates are released.

\subsection{Permutation Feature Importance on Prospective Test Data}
Standard tree-based Gini importance (or split gain) is well known in empirical software engineering to exhibit bias toward high-cardinality features or early split indicators. To provide an ecologically unassailable assessment of feature contributions, Figure~\ref{fig:importance} reports \textbf{Permutation Feature Importance} evaluated directly on the held-out prospective test set ($N_{\text{test}} = 32,536$). Permutation importance measures the exact drop in out-of-time test ROC-AUC when values of a specific feature are randomly shuffled while holding all other features constant. Crucially, release codename dummy indicators (such as \texttt{downstream\_version\_noble}) were eliminated from the feature representation, restricting the model to generalizable architectural and code attributes.

Our empirical attribution reveals a clear two-tier hierarchical risk structure: downstream packaging architecture and LTS maintenance policies serve as \textit{primary macro-level structural determinants}, establishing the baseline exposure posture for any given environment; conversely, upstream advisory scrutiny, patch complexity, and subsystem constraints function as \textit{secondary within-distribution modulators} that govern which specific patches maintainers prioritize or defer within those structural baselines.

\subsubsection{Primary Macro-Level Structural Determinants: Packaging Architecture and LTS Maintenance}
The single largest determinant of downstream exposure is the packaging pipeline itself: permuting the ecosystem indicator (\texttt{downstream\_debian} vs. \texttt{downstream\_ubuntu}) causes a massive \textbf{0.2527 drop in ROC-AUC} (100.0\% relative importance). This reflects fundamental divergence in distribution maintenance philosophies: Debian relies on wholesale kernel rebases in rolling and testing suites alongside strict minimal security backports in stable, whereas Ubuntu deploys regular, synchronized batch point updates backporting stable tree patches into active LTS kernels. 
Furthermore, the Long-Term Support indicator (\texttt{is\_lts}) induces an ROC-AUC drop of \textbf{0.0441} (17.5\% relative importance), confirming that frozen ABI constraints, backport merge friction, and multi-year legacy branch maintenance impose substantial structural resistance to prompt patch adoption across long-term distributions.

\subsubsection{Secondary Modulators: Advisory Scrutiny, Patch Complexity, and Subsystem Friction}
Within a given distribution architecture, vulnerability-specific and patch-level characteristics modulate individual remediation decisions. The initial advisory reference count (\texttt{reference\_count}) ranks as the leading secondary predictor (+0.0533 ROC-AUC drop, 21.1\% relative importance). Vulnerabilities cross-referenced across multiple bug bounties, vendor advisories, or security mailing lists command heightened public visibility and external scrutiny, compelling distribution security teams to prioritize manual triage and conflict resolution over internal routine updates.

Simultaneously, upstream patch complexity metrics independently provide discriminative signal within release baselines: patch code expansion (\texttt{loc\_added}, +0.0006 AUC), patch hunk count (\texttt{patch\_hunks}, +0.0004 AUC), files modified (\texttt{files\_changed\_count}, +0.0004 AUC), commit message documentation length (\texttt{commit\_message\_length}, +0.0003 AUC), and net churn (\texttt{loc\_delta}, +0.0002 AUC). Large diffs spanning multiple files with extensive hunks frequently fail automated cherry-picking against divergent LTS trees, requiring non-trivial manual adaptation that maintainers defer under time pressure. Finally, subsystem indicators---\texttt{affected\_component\_mm} (memory management, +0.0010 AUC) and \texttt{bluetooth} (+0.0001 AUC)---exhibit elevated friction due to complex locking semantics, low-level architectural dependencies, and hardware validation requirements.

\subsection{Per-Release Prospective Performance Breakdown}
To verify that predictive accuracy is not an artifact of a single release or temporal anomaly, we evaluated our primary Day-Zero model across each individual downstream distribution release in the prospective test set. On Ubuntu 20.04 LTS (\textit{Focal}, $N = 5,477$, 74.4\% exposed), XGBoost achieves an \textbf{ROC-AUC of 0.8214} and \textbf{PR-AUC of 0.9366}. On Ubuntu 22.04 LTS (\textit{Jammy}, $N = 5,477$, 56.6\% exposed), the model attains an \textbf{ROC-AUC of 0.8401} and \textbf{PR-AUC of 0.8959}. On Ubuntu 24.04 LTS (\textit{Noble}, $N = 5,151$, 15.0\% exposed), it achieves an \textbf{ROC-AUC of 0.7998} and \textbf{PR-AUC of 0.4245}. For Debian releases, on Debian 12 (\textit{Bookworm}, $N = 5,477$, 8.0\% exposed), XGBoost attains an \textbf{ROC-AUC of 0.7035} and \textbf{PR-AUC of 0.1506}, while on Debian 13 (\textit{Trixie}, $N = 5,477$, 1.6\% exposed), it attains an \textbf{ROC-AUC of 0.6257} and \textbf{PR-AUC of 0.0252}.

These per-release benchmarks prove that the model's discriminative ability is highest on long-standing LTS releases such as \textit{Jammy} (0.8401) and \textit{Focal} (0.8214), where backport divergence is most pronounced, demonstrating that the model learns generalizable divergence dynamics rather than memorizing any single distribution release.

\subsection{Leave-One-Release-Out (LORO) Cross-Validation and Boundary Conditions}
To provide the most rigorous proof of generalizability possible, we implemented \textbf{Leave-One-Release-Out (LORO) Cross-Validation}. In this experiment, the model is trained on observations from four distribution releases and evaluated on an entirely unseen fifth release that was never encountered during training. In this setting, the model cannot learn release-specific identifiers and must rely entirely on generalizable continuous attributes (kernel base version, mainline version distance, LTS status, patch complexity, and CWE/CVSS severity).

When evaluated across unseen mature distribution releases, the models transfer with strong discriminative fidelity: on held-out Ubuntu 22.04 (\textit{Jammy}), the model achieves an ROC-AUC of \textbf{0.8667} and PR-AUC of 0.8664; on held-out Ubuntu 20.04 (\textit{Focal}), it attains an ROC-AUC of \textbf{0.7968} and PR-AUC of 0.8685; on held-out Debian 13 (\textit{Trixie}), it achieves an ROC-AUC of \textbf{0.7762} (PR-AUC = 0.0308); and on held-out Debian 12 (\textit{Bookworm}), it achieves an ROC-AUC of \textbf{0.7523} (PR-AUC = 0.0994).

Conversely, on held-out Ubuntu 24.04 (\textit{Noble}), the model attains an ROC-AUC of \textbf{0.5827} and PR-AUC of 0.5481. This performance difference illustrates an honest and instructive empirical boundary condition: Noble was officially launched in late April 2024 with Linux kernel 6.8, placing its codebase in close architectural proximity to upstream mainline during our evaluation window. Because nascent releases exhibit minimal historical divergence and have not yet accumulated mature backport backlogs, models trained exclusively on older releases encounter a cold-start setting. While established LTS baselines transfer with high predictive power (averaging $>0.80$ ROC-AUC), newly deployed releases with near-mainline kernels require distribution-specific calibration until their downstream packaging cadences mature.

Across all held-out distribution releases, the model attains an average LORO ROC-AUC of \textbf{0.7549}. This establishes that DownstreamSec learns invariant principles of operating system patch propagation that transfer successfully to unseen distribution releases without requiring retraining.

\subsection{Retrospective Propagation Correlates: The Ablation Paradox}
In retrospective analysis on historical data, \texttt{stable\_backport\_count} displays a strong statistical correlation with downstream adoption. When an upstream commit is cleanly merged into multiple stable branches (e.g., 6.6.y, 6.1.y, 5.15.y), downstream distribution maintainers are vastly more likely to ingest the patch promptly through regular stable syncs. Conversely, when a patch is committed to upstream mainline without being tagged for stable trees, the burden of discovery and backporting falls entirely on distribution maintainers. 

However, as revealed by our ablation experiments in Table~\ref{tab:ablations}, including \texttt{stable\_backport\_count} in a day-zero model introduces temporal lookahead friction because backport commits accumulate asynchronously over weeks following disclosure. When this feature is removed, model discrimination improves to 0.8114 ROC-AUC. We therefore reframe upstream stable tree activity as an essential \textit{retrospective supply chain correlate} that explains why patches propagate, while establishing that pure day-zero prospective prediction relies on downstream code divergence and bug characteristics.

\section{Implications and Practical Guidelines for Maintainers}
\label{sec:guidelines}

Our empirical findings and predictive models suggest concrete, actionable recommendations for open-source ecosystem stakeholders:

\subsection{Recommendations for Downstream Distribution Teams}
Downstream distribution security teams should deploy automated early-warning triage pipelines powered by pre-remediation exposure models. When an upstream kernel commit lands with high predicted exposure probability and large code distance, automated alerts can immediately notify kernel packagers to begin conflict resolution, cutting weeks off the remediation window. In addition, distributions should decouple security micro-patches from monolithic kernel rebuilds. Adopting live-patching technologies (such as \texttt{kpatch} or \texttt{livepatch}) for isolated high-risk security patches can close the 250-day exposure gap without waiting for full ABI-stabilized kernel rebuilds.

\subsection{Recommendations for Upstream Kernel Maintainers}
Because stable branch inclusion is the strongest driver of downstream adoption, upstream authors must consistently use \texttt{Cc: stable@vger.kernel.org} tags on security-relevant fixes. Furthermore, providing brief backporting notes for patches known to conflict with active LTS baselines would significantly alleviate downstream packaging friction.

\subsection{Recommendations for Enterprise Infrastructure Operators}
Enterprise compliance teams often mark vulnerabilities as remediated as soon as an upstream CVE is announced as fixed. Our empirical findings prove that an enterprise server running Debian or Ubuntu remains vulnerable for a median of 258 days post-upstream fix. Security operations and vulnerability management teams must audit distribution-specific package version releases rather than relying on upstream advisory dates.

\section{Threats to Validity}
\label{sec:threats}

We identify and address potential threats to the validity of our study:

\subsection{Construct Validity}
Construct validity concerns whether our metrics accurately capture downstream exposure. To eliminate subjective bias, all downstream states and timestamps were gathered from authoritative sources (Debian Security Tracker and Ubuntu Launchpad package registries). Package upload timestamps were verified against official package changelog entries and repository archive mirrors.

\subsection{Internal Validity}
Internal validity concerns confounding factors and data leakage. We strictly enforced an out-of-time prospective split ($\le$2023 train, $\ge$2024 test), preventing any lookahead leakage. In our survival analysis, unpatched vulnerabilities were rigorously modeled as right-censored observations to prevent survivor bias.

\subsection{External Validity}
External validity concerns the generalizability of our findings. While our empirical study focused directly on Debian and Ubuntu, these two distributions form the upstream foundation for widely deployed downstream derivatives, including Linux Mint, Pop!\_OS, and major public cloud server images. We hypothesize that these derivative distributions experience comparable or compounded remediation delays due to downstream dependency inheritance and additional packaging cycles; however, we explicitly frame this as an empirical hypothesis for future verification, as their binary packages and repository archives were not directly evaluated in this study. Furthermore, Debian and Ubuntu represent two archetypal packaging paradigms: a community rolling/testing model and an enterprise LTS model. Future work will extend DownstreamSec to independently measure downstream derivatives, the RPM ecosystem (Fedora/RHEL), and musl-based distributions (Alpine Linux).

\subsection{Conclusion Validity}
Conclusion validity concerns the statistical power of our inferences. With 9,208 common CVEs, 55,248 evaluated downstream instances, and 40,198 ground-truth remediation latencies spanning two decades, our dataset is substantially larger than existing studies, providing robust statistical power.

\section{Related Work}
\label{sec:related}

\subsection{Software Supply Chain and Dependency Lag}
A growing body of research investigates security lag in open-source dependencies. Kula et al.~\citep{kula2018empirical} and Alfadel et al.~\citep{alfadel2021empirical} examined update delays in library dependencies, finding that developers are reluctant to update dependencies due to fear of breaking changes. Pashchenko et al.~\citep{pashchenko2020vulnerable} demonstrated that counting vulnerable dependencies without assessing reachable call paths inflates perceived risk. While these works address application-level package managers, our study investigates operating system kernel supply chains across upstream and downstream distributions, complementing earlier multi-distribution empirical surveys (e.g., De Coster et al.~\citep{decoster2022measuring}) by linking upstream Git commit mechanics directly to prospective Day-Zero machine learning models.

\subsection{Operating System and Kernel Vulnerability Lifecycle}
The lifecycle of vulnerabilities in operating systems has been explored by Ruohonen et al.~\citep{ruohonen2018empirical, ruohonen2019tracking}, who analyzed vulnerability lifetimes in Debian packages. Wang et al.~\citep{wang2020empirical} conducted an empirical study on the propagation of security bugs within upstream Linux kernel branches. De Coster et al.~\citep{decoster2022measuring} surveyed patch lag across multiple Linux distributions using web scrapers. Our work advances this literature by triangulating the complete common intersection of 9,208 CVEs across upstream and downstream trackers, formalizing a 7-state taxonomy with empirical manual validation, and developing prospective machine learning models that forecast downstream exposure before remediation occurs.

\subsection{Predictive Vulnerability Modeling}
Machine learning has been widely applied to predict software vulnerability characteristics, including component vulnerability~\citep{neuhaus2009predicting, scandariato2014predicting}, exploitability~\citep{freitas2021predicting}, and patching time~\citep{saha2018understanding}. However, prior vulnerability prediction studies frequently employ unstratified random cross-validation, which suffers from severe temporal lookahead leakage~\citep{zimmermann2010predicting}. Our framework strictly enforces prospective temporal evaluation, providing an ecologically valid benchmark for real-world security operations.

\section{Conclusion and Future Work}
\label{sec:conclusion}

In this paper, we presented \textbf{DownstreamSec}, the largest longitudinal empirical study and prospective predictive modeling framework of vulnerability propagation from the Linux kernel to downstream Debian and Ubuntu distributions. Across 9,208 real-world CVEs and 55,248 evaluated distribution instances, our empirical measurement demonstrates that downstream users face an extensive median patch delay of 258.8 days (from upstream commit) and 274.6 days (from public CVE disclosure), with 69.3\% of resolved vulnerabilities requiring more than three months to receive package fixes (Kaplan-Meier survival probability $\hat{S}(90) = 0.7764$ [95\% CI: 0.7729, 0.7799]).

To address this exposure window, we developed strict day-zero pre-remediation machine learning models that forecast downstream security exposure at upstream disclosure time with an ROC-AUC of 0.8114 [95\% CI: 0.8066, 0.8159] (XGBoost) and 75.48\% balanced accuracy (Logistic Regression) under an out-of-time evaluation protocol, completely omitting post-disclosure stable backport features and pruning pre-release anachronisms. We demonstrated that downstream packaging architecture and LTS maintenance policy serve as primary structural determinants of risk, with upstream patch complexity and subsystem scrutiny acting as secondary modulators, achieving a $2.14\times$ triage precision lift over baseline prevalence and transferring effectively to unseen distributions under Leave-One-Release-Out cross-validation (mean ROC-AUC = 0.7549, exceeding 0.75--0.87 across mature LTS releases, while identifying nascent releases with near-mainline baselines such as Ubuntu Noble at 0.5827 as a recognized operational boundary condition).

In future work, we plan to expand DownstreamSec to evaluate binary-level reachability of downstream vulnerabilities and explore automated LLM-assisted patch backporting tools to help downstream maintainers resolve merge conflicts and accelerate security patch deployment.

\section{Upstream Commit Mapping and Verification Protocol}
\label{app:commit_mapping}
Linking CVE records to upstream Linux kernel fix commits required a three-stage triangulation pipeline:
First, official Git commit hashes were extracted from the Linux Kernel CVE Project repository (\texttt{vulns/R/}), which publishes structured JSON 5.0 records maintained by kernel maintainers.
Second, for CVE records originating prior to the Linux CNA transition, commit URLs were extracted from NVD references matching \url{git.kernel.org} upstream commit paths.
Third, downstream changelog entries from Debian and Ubuntu were mined for upstream commit references in \texttt{debian/patches/} series files and \texttt{Patch: upstream:} tags in the Ubuntu Security Tracker. Every identified commit hash was validated against a local mirror of \texttt{torvalds/linux.git} using \texttt{git cat-file -e <hash>} to confirm physical commit existence and extract immutable author dates, parent hashes, modified files, and lines of code churn.

\section{Release-Time Validity Protocol and Chronology Matrix}
\label{app:release_validity}
To prevent anachronisms in prospective evaluation, each $(cve, release)$ instance is strictly filtered according to the public release launch date:
\begin{itemize}
\item \textbf{Debian 12 (\textit{Bookworm})}: Launched June 10, 2023.
\item \textbf{Debian \textit{Sid} (Unstable)}: Continuous rolling release (valid across all evaluated years).
\item \textbf{Debian 13 (\textit{Trixie})}: Staged June 10, 2023.
\item \textbf{Ubuntu 20.04 LTS (\textit{Focal})}: Launched April 23, 2020.
\item \textbf{Ubuntu 22.04 LTS (\textit{Jammy})}: Launched April 21, 2022.
\item \textbf{Ubuntu 24.04 LTS (\textit{Noble})}: Launched April 25, 2024.
\end{itemize}
Any observation where a CVE's disclosure timestamp preceded a distribution's official launch date was pruned. Exactly 508 pre-release instances of Ubuntu Noble were pruned for CVEs disclosed between January 1, 2024 and April 24, 2024, leaving $N_{\text{test}} = 32,536$ valid prospective test instances ($N_{\text{train}} = 22,204$ historical training instances).

\section{Data Preprocessing and Imputation Protocols}
\label{app:preprocessing}
Missing values in numerical features (e.g., CVSS base score when an advisory is under initial analysis) were imputed using the median computed strictly over the historical training set ($D_{\text{train}}$). Numerical features were standardized using $Z$-score normalization ($x' = (x - \mu_{\text{train}}) / \sigma_{\text{train}}$). Categorical variables (attack vector, attack complexity, affected subsystem, vulnerability classification) were transformed using one-hot encoding fitted exclusively on $D_{\text{train}}$ with \texttt{handle\_unknown='ignore'}. To prevent target memorization, distribution release codenames were omitted from the primary feature representation.

\section{Complete 46-Feature Schema Specification}
\label{app:features}
The primary generalizable Day-Zero feature matrix encompasses 46 features:
\begin{itemize}
\item \textit{Downstream Packaging Architecture (3 features)}: Downstream ecosystem indicator (\texttt{downstream\_debian}, \texttt{downstream\_ubuntu}), numerical downstream base kernel version (\texttt{downstream\_kernel\_ver}: 5.4, 5.15, 6.1, 6.8, 6.12), and Long-Term Support indicator (\texttt{is\_lts}).
\item \textit{Upstream Patch Complexity (8 features)}: Count of modified files (\texttt{files\_changed\_count}), lines added (\texttt{loc\_added}), lines deleted (\texttt{loc\_deleted}), net LOC delta (\texttt{loc\_delta}), hunk frequency (\texttt{patch\_hunks}), commit message character length (\texttt{commit\_message\_length}), single-file surgical fix flag (\texttt{is\_single\_file\_fix}), and initial advisory references (\texttt{reference\_count}).
\item \textit{Vulnerability Severity and Subsystems (35 features)}: CVSS v3.1 base score, attack vector (Network, Adjacent Network, Local, Physical, Unknown), attack complexity (Low, High, Unknown), standardized CWE classification one-hot encodings (out-of-bounds read/write, use-after-free, null pointer dereference, memory leak, integer overflow, concurrency race, other), and affected kernel subsystem indicators (\texttt{net}, \texttt{fs}, \texttt{drivers}, \texttt{mm}, \texttt{kernel}, \texttt{arch}, \texttt{block}, \texttt{crypto}, \texttt{sound}, \texttt{security}, \texttt{bluetooth}, \texttt{ext4}, \texttt{netfilter}, \texttt{bpf}, \texttt{other}).
\end{itemize}
