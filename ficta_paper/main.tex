\maketitle

\abstract{When developers fix a security bug in the upstream Linux kernel, public databases often report the flaw as resolved. However, downstream enterprise systems like Debian and Ubuntu do not receive this fix immediately. Distribution maintainers cannot simply copy new code into production releases; they must backport and test patches across older Long-Term Support (LTS) kernels to protect system stability. In this paper, we study this downstream delay through \textbf{DownstreamSec}, an empirical study and predictive framework examining how kernel vulnerabilities travel from upstream commits to Debian and Ubuntu releases. By tracking 9,208 verified vulnerabilities and 55,248 release instances across four authoritative security platforms over two decades, we find that downstream fixes take a median of 258.8 days---over eight months---from upstream commit to reach users, with 77.6\% of flaws unpatched after 90 days. To help security teams manage this backlog, we develop machine learning models using only Day-Zero data available on the day of public disclosure. On unseen prospective data from 2024--2025 ($N_{\text{test}} = 32,536$), our models forecast downstream exposure with an ROC-AUC of 0.8114 (XGBoost) and 75.48\% balanced accuracy (Logistic Regression). In practice, screening the top 50\% highest-risk items captures 94.3\% of prolonged exposures, cutting maintainer review workloads in half and showing that packaging policies, rather than patch code churn, govern downstream risk.
\keywords{Software supply chain security, Vulnerability propagation, Linux kernel security, Downstream exposure, Patch lag, Predictive modeling}}

\section{Introduction}
\label{sec:intro}

Most enterprise servers, cloud platforms, and container systems run on Linux distributions such as Debian and Ubuntu. At the core of these systems is the Linux kernel. When a vulnerability is found in the kernel, upstream developers commit a fix to Linus Torvalds' repository and assign it a Common Vulnerabilities and Exposures (CVE) identifier.

Vulnerability scanners often treat this upstream commit as the moment of resolution, showing green status reports to operators~\cite{gkortzis2021software, decoster2022measuring}. But in practice, an upstream Git commit provides no protection to a running machine. For example, in CVE-2023-32233 (a local privilege escalation bug in Netfilter), upstream merged a fix on May 8, 2023. Vulnerability scanners immediately marked the issue resolved. Yet on production servers running Ubuntu 20.04 LTS (kernel 5.4) and Debian 11 (kernel 5.10), that commit changed nothing. Due to code differences between upstream and older enterprise kernels, automated patch application failed. Maintainers had to manually adapt patch hunks, test for regressions, and wait for scheduled kernel update packages. As a result, production servers remained exposed for months after the fix was publicly known.

This gap exists because downstream distributions keep their kernel code stable for five to ten years to protect binary compatibility and prevent unexpected breakage~\cite{ruohonen2019tracking}. While prior research has examined update lag in package managers like npm and PyPI~\cite{alfadel2021empirical, kula2018empirical, pashchenko2020vulnerable}, operating system kernels present distinct challenges: replacing a kernel component cannot be done without risking boot failures or hardware incompatibilities. Moreover, prior studies of OS security have often used smaller samples, examined only one distribution, or used evaluations susceptible to temporal data leakage~\cite{zimmermann2010predicting}.

Our study shows that downstream patch delays follow understandable patterns based on code divergence and release lifecycles. More importantly, this exposure can be predicted on Day Zero, helping security teams focus on difficult backports early. We investigate three research questions:
In \textbf{RQ1 (Predictive Modeling)}, can downstream security exposure be predicted at disclosure time using only Day-Zero data?
In \textbf{RQ2 (Empirical Patch Lag)}, how long do downstream systems remain exposed under supply-chain and public disclosure timelines?
In \textbf{RQ3 (Key Drivers and Determinants)}, which vulnerability, patch, and packaging factors best explain exposure risk?

This paper makes five main contributions:
(1) \textbf{An Audited Security Taxonomy ($D0$--$D6$)}: We define a seven-state taxonomy of backporting outcomes, validated by human raters ($\kappa = 0.948$) and automated consensus ($\kappa = 0.981$, Section~\ref{sec:background});
(2) \textbf{A Multi-Source Longitudinal Dataset}: We cross-reference NVD, the Linux Kernel CVE team, Debian, and Ubuntu, tracking 9,208 common CVEs across six releases (55,248 observations) over two decades (Section~\ref{sec:curation});
(3) \textbf{Empirical Latency Measurement and Survival Analysis}: Across 40,198 confirmed fixes, we measure an empirical median patch lag of 258.8 days from upstream commit (274.6 days from disclosure), with a 90-day survival probability $\hat{S}(90) = 0.7764$ (Section~\ref{sec:latency});
(4) \textbf{Strict Day-Zero Prospective Exposure Forecasting}: Under an anti-leakage temporal split ($\le$2023 train, $\ge$2024 test; $N_{\text{test}} = 32,536$), our models forecast downstream exposure with an ROC-AUC of 0.8114 (XGBoost) and 75.48\% Balanced Accuracy (Logistic Regression), delivering a triage policy that captures 94.3\% of prolonged exposures in the top 50\% screening queue (Section~\ref{sec:modeling}); and
(5) \textbf{Structural Feature Attribution and Transferability}: Permutation analysis shows that downstream packaging architecture and LTS policy are primary drivers of risk, and Leave-One-Release-Out validation confirms strong model transferability across releases (mean ROC-AUC = 0.7549, Section~\ref{sec:importance}).

\section{Ecosystem Background and Downstream Security Taxonomy}
\label{sec:background}

Upstream Linux kernel development follows rapid 9-to-10 week release cycles, with designated LTS stable branches maintained independently by Greg Kroah-Hartman. Downstream distributions handle these updates differently: Debian follows a community rolling model (\textit{sid}, \textit{trixie}) that periodically rebases onto newer stable kernels, alongside a frozen stable model (\textit{bookworm} on Linux 6.1) that applies minimal backports. Ubuntu freezes each LTS suite on a specific kernel (20.04 \textit{Focal} on 5.4, 22.04 \textit{Jammy} on 5.15, 24.04 \textit{Noble} on 6.8), deploying synchronized batch point updates.

\textit{The Packager's Workflow}: When a security patch appears upstream, packagers must deal with code differences across branches. Rather than using an oversimplified binary patched/unpatched label, we define a seven-state taxonomy ($D0$--$D6$) that captures actual downstream security states:
\textbf{D0 (Not Affected)}: vulnerable code absent due to version boundaries or disabled config flags;
\textbf{D1 (Vulnerable / Unresolved)}: vulnerable code present and unpatched in production archives;
\textbf{D2 (Clean Upstream Merge)}: upstream patch applied cleanly without code modification;
\textbf{D3 (Adapted Backport)}: maintainers authored non-trivial code adaptations to resolve merge conflicts;
\textbf{D4 (Mitigated / Workaround)}: neutralized through configuration or compiler flags without code patches;
\textbf{D5 (Won't Fix)}: maintainers explicitly decide against patching (e.g., deprecated subsystem); and
\textbf{D6 (End-of-Life / Unsupported)}: release reached end-of-life.

A manual audit of 100 stratified CVE-release samples by two human raters showed high inter-rater agreement (97.0\%, Cohen's $\kappa = 0.948$~\cite{cohen1960coefficient}), and human consensus matched our automated pipeline on 99 of 100 cases ($\kappa = 0.981$). Figure~\ref{fig:taxonomy} shows how these security states are distributed across all six evaluated releases. In active production releases, states $D4$ (partial fix) and $D5$ (won't fix) account for 0.0\% of records because Debian and Ubuntu treat the kernel as core infrastructure, requiring full backports ($D2$/$D3$) for verified CVEs rather than workarounds or unpatched waivers. State $D6$ (EOL) is excluded by our release validity filtering.

\section{Longitudinal Multi-Source Dataset Construction}
\label{sec:curation}

To build a reliable dataset of vulnerability propagation, we collect and cross-reference data from four platforms: (1)~\textit{NVD} for disclosure dates and severity ratings (12,176 raw CVEs); (2)~the official \textit{Linux Kernel CVE Repository} for Git fixing commits and stable backport tags (9,469 JSON 5.0 records); (3)~the \textit{Debian Security Tracker} for package states in Debian (10,131 records); and (4)~the \textit{Canonical Ubuntu Security Tracker} for patch releases across Ubuntu LTS suites (9,210 curated records). Finding the exact intersection across all four sources yields \textbf{9,208 common, verified CVEs} with full ground truth across all platforms. Tracking each vulnerability across six active releases produces \textbf{55,248 release observations}, structured into four tables (Table~\ref{tab:schema}).

To prevent predictive models from using future data, we apply a strict \textbf{Release-Time Validity Protocol}. We remove 508 records where a vulnerability was disclosed before the target distribution was released (specifically early-2024 CVEs evaluated against Ubuntu 24.04 Noble, which launched on April 25, 2024). This leaves \textbf{54,740 valid release instances} ($N_{\text{train}} = 22,204$, $N_{\text{test}} = 32,536$). Across these valid instances, we identify \textbf{40,198 confirmed remediation events} with complete package timestamps (a 73.4\% resolution rate).

\section{Empirical Measurement of Downstream Patch Lag (RQ2)}
\label{sec:latency}

\subsection{Dual Latency Metrics and Real-World Timelines}

When a kernel vulnerability is fixed, attackers and system administrators operate on different timelines. An upstream Git commit and a public CVE advisory rarely happen on the same day. We measure both timelines:
\textbf{The Supply-Chain Window} ($\Delta t_{\text{upstream}} = t_{\text{downstream}} - t_{\text{upstream}}$) measures calendar days from the upstream Git commit to the downstream package upload. This captures the window during which attackers can inspect public commits while downstream servers remain unpatched.
\textbf{The Public Disclosure Window} ($\Delta t_{\text{disclosure}} = t_{\text{downstream}} - t_{\text{disclosure}}$) measures the time between NVD publication and downstream package deployment, representing the window when administrators are aware of the threat.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.88\textwidth,height=2.9cm,keepaspectratio]{figures/fig1_survival_remediation_latency.pdf}
\caption{Downstream remediation dynamics: (Left) Empirical cumulative distribution of patch delay across 40,198 resolved vulnerabilities; (Right) Kaplan-Meier survival curves comparing patch lag between Debian and Ubuntu.}
\label{fig:survival}
\end{figure}

Measuring these timelines across 40,198 confirmed fixes shows that downstream patching takes substantial time. Under the \textbf{Supply-Chain Window} ($\Delta t_{\text{upstream}}$), fixes take an average of \textbf{306.60 days} ($\approx 10.1$ months) and a median of \textbf{258.77 days} ($\approx 8.5$ months) to reach users. Fully \textbf{69.3\%} of resolved vulnerabilities take longer than 90 days, and \textbf{21.4\%} take over a year. Under the \textbf{Public Disclosure Window} ($\Delta t_{\text{disclosure}}$), 93.1\% of instances ($N = 37,415$) were patched on or after disclosure, with a median lag of \textbf{274.59 days} (mean 327.02 days, 74.2\% $>90$ days, and 40.2\% $>365$ days). A smaller fraction (6.9\%, $N = 2,783$) appeared to be resolved before formal disclosure; rather than early patching, this occurs when the Linux kernel security team bulk-assigned historical CVE IDs in early 2024 to commits merged years earlier.

\subsection{Survival Analysis: Debian vs. Ubuntu}

Because some vulnerabilities remain unpatched at data collection, averaging only resolved cases would underestimate exposure. We use non-parametric \textbf{Kaplan-Meier survival analysis}~\cite{kaplan1958nonparametric} to account for right-censoring:
\begin{equation}
\hat{S}(t) = \prod_{t_i \le t} \left(1 - \frac{d_i}{n_i}\right)
\end{equation}
where $t_i$ represents distinct event times, $d_i$ is the number of packages patched at $t_i$, and $n_i$ represents vulnerable instances still awaiting a fix immediately before $t_i$. Computing confidence intervals with Greenwood's formula, the empirical probability that an affected system remains unpatched is $\hat{S}(30) = 0.8735$ [95\% CI: 0.8707, 0.8763], $\hat{S}(90) = 0.7764$ [95\% CI: 0.7729, 0.7799], $\hat{S}(180) = 0.7106$ [95\% CI: 0.7068, 0.7144], and $\hat{S}(365) = 0.5467$ [95\% CI: 0.5425, 0.5508]. In other words, roughly three out of four vulnerable systems remain unpatched three months after disclosure, and over half remain unpatched after a year.

As illustrated in Figure~\ref{fig:survival}, the survival curves mirror the distinct engineering cultures of the two distributions. Debian rolling releases display steep vertical drops whenever the distribution rebases onto a newer kernel, wiping out large backlogs of vulnerabilities in a single sweep; its frozen stable releases, by contrast, plateau as backports taper off. Ubuntu displays steady, stair-stepped declines corresponding to its scheduled point-update kernel builds.

\section{Predictive Modeling of Downstream Security Exposure (RQ1)}
\label{sec:modeling}

\subsection{Formulation and Out-of-Time Protocol}

To help security teams get ahead of this lag, we cast downstream exposure prediction as a supervised binary classification problem. For any given vulnerability and target release, our model predicts $y \in \{0, 1\}$ directly from distribution tracker ground truth:
\textbf{Exposed ($y = 1$)}: The target release is actively affected and unpatched in production archives ($D1\_vulnerable$, including statuses \texttt{needed}, \texttt{unfixed}, \texttt{open}, and \texttt{deferred}) or partially mitigated ($D4\_partial\_fix$).
\textbf{Protected ($y = 0$)}: The system is secure---either because vulnerable code was never included in that release ($D0\_not\_affected$, statuses \texttt{not-affected}, \texttt{DNE}), or because a patch has been integrated ($D2\_fixed\_equivalent$, $D3\_modified\_fix$), or the flaw is determined not to require backporting ($D5\_wont\_fix$, e.g., unreachable config). Releases that have reached end-of-life ($D6\_eol$) are excluded by our validity filtering.

\textit{Reconciling Latency and Classification}: While survival analysis (Section~\ref{sec:latency}) measures the velocity of completed fixes ($N = 40,198$), our classifier evaluates all active and pending packages at a snapshot, labeling unresolved instances as exposed ($y = 1$). This explains why dataset positive rates (28.21\% in train, 26.05\% in test) differ from the 90-day survival probability $\hat{S}(90) = 0.7764$: classification assesses whether a server is currently vulnerable versus safe, whereas survival curves track how quickly resolved patches were delivered.

To mirror real-world deployment, we enforce a strict \textbf{anti-leakage temporal split} with release-time validity, training on CVEs disclosed up to 2023 ($N_{\text{train}} = 22,204$) and evaluating prospectively on unseen bugs from 2024--2025 ($N_{\text{test}} = 32,536$). Encoders are fit strictly on training data. Our feature representation relies solely on information visible on Day Zero across 52 attributes (46 without release dummies): (1)~vulnerability traits (35 features: CVSS score, vector, complexity, 15 kernel subsystems, and 10 collapsed CWE classes grouped from $>65$ NVD identifiers); (2)~upstream patch complexity (7 features: lines added/deleted, churn, hunk count, modified file count, and commit message length); and (3)~downstream architecture (10 features: distribution family, release indicators, base kernel versions, and LTS status). In our dataset, 99.97\% of upstream fixing commits ($N = 9,205$) strictly predate or coincide with public disclosure ($t_{\text{upstream\_commit}} \le t_{\text{disclosure}}$), guaranteeing that patch complexity attributes are available at disclosure. Dynamic post-disclosure features (such as Git stable backport counts) are completely excluded.

\section{Feature Attribution, Cross-Release Transfer, and Boundary Conditions (RQ3)}
\label{sec:importance}

\begin{figure}[htbp]
\centering
\includegraphics[width=0.80\textwidth,height=2.7cm,keepaspectratio]{figures/fig3_feature_importance.pdf}
\caption{Prospective permutation feature importance evaluated on the out-of-time test set ($N_{\text{test}} = 32,536$), reporting the reduction in prospective ROC-AUC when each feature is permuted (zero post-disclosure features, release codename dummies excluded).}
\label{fig:importance}
\end{figure}

To understand what factors drive exposure risk without impurity bias, Figure~\ref{fig:importance} reports \textbf{Permutation Feature Importance} on the held-out prospective test set ($N_{\text{test}} = 32,536$). Measuring the decrease in ROC-AUC when features are permuted reveals two main levels of influence:

\textit{1. Downstream Architecture}: Distribution packaging policies set baseline exposure risk. Shuffling the distribution indicator (\texttt{downstream\_debian} vs. \texttt{ubuntu}) causes a \textbf{0.2527 drop in ROC-AUC} (100.0\% relative importance). This difference reflects release workflows: Debian rolling branches periodically rebase onto newer kernels, whereas Ubuntu LTS uses scheduled point-update batches. When release indicator variables are removed (Figure~\ref{fig:importance}), structural features---particularly LTS status (\texttt{is\_lts}, causing a \textbf{0.0441} drop in ROC-AUC, 17.5\% relative importance) and base kernel version---remain the strongest drivers of exposure risk.

\textit{2. Vulnerability and Patch Traits}: Within a given distribution release, bug traits and patch complexity affect individual fix times. External attention (\texttt{reference\_count}) is the leading secondary predictor (+0.0533 AUC drop, 21.1\% relative importance), as widely discussed bugs receive faster attention. Upstream patch complexity provides additional signal: added lines (\texttt{loc\_added}, +0.0006 AUC), hunk count (\texttt{patch\_hunks}, +0.0004 AUC), modified file count (\texttt{files\_changed\_count}, +0.0004 AUC), and commit message length (\texttt{commit\_message\_length}, +0.0003 AUC). Larger patches often conflict with older codebases, requiring manual edits. Subsystems like memory management (\texttt{affected\_component\_mm}, +0.0010 AUC) and \texttt{bluetooth} (+0.0001 AUC) also show higher friction due to complex concurrency and hardware dependencies.

Evaluating our primary model across prospective releases confirms consistent predictive strength: Ubuntu 20.04 LTS (\textit{Focal}) achieves ROC-AUC = \textbf{0.8214} (PR-AUC = 0.9366); Ubuntu 22.04 LTS (\textit{Jammy}) attains ROC-AUC = \textbf{0.8401} (PR-AUC = 0.8959); Ubuntu 24.04 LTS (\textit{Noble}) achieves ROC-AUC = \textbf{0.7998} (PR-AUC = 0.4245); Debian 12 (\textit{Bookworm}) attains ROC-AUC = \textbf{0.7035}; and Debian 13 (\textit{Trixie}) attains ROC-AUC = \textbf{0.6257}. In our temporal evaluation, release encoders are fit on historical training data with \texttt{handle\_unknown='ignore'} (mapping unseen suites to an all-zero vector, while generalizable architectural traits like \texttt{downstream\_kernel\_ver} and \texttt{is\_lts} preserve continuity). Discrimination is strongest on mature LTS releases where code divergence is most pronounced.

Under \textbf{Leave-One-Release-Out (LORO) Cross-Validation} (training on four releases and evaluating on an unseen fifth release without release dummies), models transfer strongly across mature LTS suites: held-out Ubuntu 22.04 (\textit{Jammy}) achieves ROC-AUC = \textbf{0.8667} (PR-AUC = 0.8664); held-out Ubuntu 20.04 (\textit{Focal}) attains ROC-AUC = \textbf{0.7968}; held-out Debian 13 (\textit{Trixie}) achieves ROC-AUC = \textbf{0.7762}; and held-out Debian 12 (\textit{Bookworm}) achieves ROC-AUC = \textbf{0.7523}.

On held-out Ubuntu 24.04 (\textit{Noble}), the transfer model attains an ROC-AUC of \textbf{0.5827} (PR-AUC = 0.5481), highlighting an honest boundary condition: Noble launched in late April 2024 running Linux 6.8, in close proximity to upstream mainline during our snapshot. Because brand-new releases have not yet diverged significantly and have not accumulated mature backport backlogs, models evaluated out-of-release encounter a cold-start setting. Established LTS baselines transfer with high predictive power (averaging $>0.80$ ROC-AUC), while newly deployed releases benefit from brief calibration as packaging cadences stabilize. Across all held-out releases, the model maintains an average LORO ROC-AUC of \textbf{0.7549}.

\section{Practical Implications and Threats to Validity}
\label{sec:guidelines}

Our findings offer practical guidance across the software supply chain. For \textbf{downstream packagers}, waiting for public CVE advisories leaves systems exposed for hundreds of days; maintainers should deploy automated day-zero triage to flag difficult backports the day upstream commits land, leveraging live-patching tools (\texttt{kpatch}, \texttt{livepatch}) to deliver urgent fixes without waiting for monolithic rebuild cycles. For \textbf{upstream maintainers}, backport friction decreases substantially when developers annotate patches with \texttt{Cc: stable@vger.kernel.org} and document tricky dependencies. For \textbf{enterprise security teams}, vulnerability scanners must audit installed package versions rather than upstream Git commit dates: upstream fixes provide zero protection until downstream packages are rebuilt and deployed.

We address four threats to validity:
(1)~\textit{Construct}: All downstream states and timestamps were ingested directly from official Debian and Ubuntu trackers and verified against package changelogs.
(2)~\textit{Internal}: We enforced strict out-of-time splits ($\le$2023 train, $\ge$2024 test), pruned pre-release anachronisms, and treated unpatched flaws as right-censored cases using Kaplan-Meier curves.
(3)~\textit{External}: While focused on Debian and Ubuntu kernel ecosystems, these platforms form the foundation for hundreds of derivative distributions, cloud images, and container operating systems (e.g., Linux Mint, Pop!\_OS), which inherit identical delays.
(4)~\textit{Conclusion and Sampling}: Requiring intersection across all four trackers isolates high-quality ground truth ($N = 9,208$ common CVEs, 55,248 observations). While this focus may mildly under-represent unconfirmed upstream reports, it ensures every analyzed record represents an authenticated issue with complete supply-chain provenance.

\section{Related Work}
\label{sec:related}

\textit{Software Supply Chains and Dependency Lag}: Studies by Kula et al.~\cite{kula2018empirical} and Alfadel et al.~\cite{alfadel2021empirical} demonstrated that developers frequently delay updating libraries in user-space registries (npm, PyPI, Maven) to avoid breaking software. Pashchenko et al.~\cite{pashchenko2020vulnerable} showed that counting vulnerable libraries without checking reachability overstates operational risk. Our work extends empirical supply-chain analysis to operating system kernels, where ABI stability must be maintained across multi-year LTS cycles~\cite{decoster2022measuring}.

\textit{Operating System Vulnerability Lifecycles}: Longitudinal analyses by Ruohonen et al.~\cite{ruohonen2018empirical, ruohonen2019tracking} traced vulnerability lifetimes across thousands of Debian packages. Wang et al.~\cite{wang2020empirical} investigated how security bugs propagate across upstream Linux kernel branches. DownstreamSec synthesizes these lines of inquiry: by triangulating 9,208 common CVEs across upstream Git, NVD, Debian, and Ubuntu, we formalize an audited taxonomy ($\kappa = 0.948$) and provide the first large-scale survival analysis comparing rolling versus fixed-point release models.

\textit{Predictive Vulnerability Modeling}: Machine learning has long been applied to software security, including component vulnerability prediction~\cite{scandariato2014predicting}, exploitability forecasting~\cite{freitas2021predicting}, and patch duration analysis~\cite{saha2018understanding}. As Zimmermann et al.~\cite{zimmermann2010predicting} noted, software prediction models often suffer from subtle temporal leakage. To avoid this pitfall, DownstreamSec enforces prospective out-of-time splits ($\le$2023 train, $\ge$2024 test), filters pre-release records, and uses Leave-One-Release-Out evaluation to ensure realistic benchmarks.

\section{Conclusion and Future Work}
\label{sec:conclusion}

Downstream vulnerability exposure in open-source operating systems is driven by structural packaging dynamics rather than upstream code churn alone. Across 55,248 release observations spanning Debian and Ubuntu over two decades, downstream servers endure a median patch delay of 258.8 days after an upstream fix is committed, with 77.6\% remaining exposed past 90 days. Furthermore, this exposure is predictable on Day Zero: pre-remediation signals forecast downstream exposure with an ROC-AUC of 0.8114, enabling an operational triage policy that catches 94.3\% of protracted exposures while cutting maintainer review queues in half.

Shortening the upstream-to-downstream delay requires two practical steps: (1)~automated patch-backporting tools that use Day-Zero triage signals to resolve conflicts before human review; and (2)~wider use of kernel live-patching to deliver security updates without waiting for full rebuild cycles.
