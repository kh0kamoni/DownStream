\abstract{When a security vulnerability in the Linux kernel is resolved upstream, public trackers often report the flaw as fixed. In reality, millions of enterprise servers running downstream distributions like Debian and Ubuntu remain vulnerable. Downstream maintainers cannot simply copy new code into production-stable systems; they must carefully adapt each fix across divergent Long-Term Support (LTS) kernel baselines to preserve system stability, creating an unmeasured window of exposure. In this paper, we present \textbf{DownstreamSec}, a large-scale empirical study and predictive framework examining how kernel vulnerabilities actually travel from upstream commits to downstream releases. Tracking 9,208 verified vulnerabilities and 55,248 release instances across four authoritative platforms over two decades, we find that downstream fixes require an empirical median of 258.8 days---over eight months---to reach users, with 77.6\% of vulnerabilities remaining unpatched after 90 days. To help security teams tackle this backlog, we develop an early-warning machine learning model using only information available on the day a bug is disclosed. Evaluated on unseen real-world data from 2024--2025, our model forecasts downstream exposure with an ROC-AUC of 0.8114 and 75.5\% balanced accuracy. In operational triage, screening just the top 50\% of flagged vulnerabilities captures 94.3\% of protracted exposures, halving maintainer review workloads and showing that packaging architecture, rather than patch code churn, governs downstream risk.
\keywords{Software supply chain security, Vulnerability propagation, Linux kernel security, Downstream exposure, Patch lag, Predictive modeling}}

\section{Introduction}
\label{sec:intro}

Most of today's digital world---from hyperscale cloud instances and Kubernetes clusters to critical banking systems---runs on open-source Linux distributions, chief among them Debian and Ubuntu. At the operational foundation of these platforms resides the Linux kernel. When security researchers discover a vulnerability in the kernel, upstream developers merge a fix into Linus Torvalds' mainline Git repository and assign it a Common Vulnerabilities and Exposures (CVE) identifier.

Vulnerability databases and automated compliance scanners routinely celebrate this moment, displaying green checkmarks and reassuring security teams that the flaw is resolved~\cite{gkortzis2021software, decoster2022measuring}. But in production environments, an upstream Git commit provides zero protection to a running server. Consider CVE-2023-32233, a severe local privilege escalation flaw in the Netfilter nf\_tables subsystem: upstream merged the fix on May 8, 2023, and public scanners immediately marked the issue ``remediated.'' Yet for production servers running Ubuntu 20.04 LTS (kernel 5.4) and Debian 11 (kernel 5.10), that upstream Git commit changed nothing. Upstream refactoring caused automated cherry-picking to fail against older Long-Term Support (LTS) codebases, forcing downstream maintainers to rewrite patch hunks by hand, test for breaking changes, and wait for scheduled batch kernel rebuilds. Consequently, enterprise servers remained silently exposed to exploitation for months after the fix was publicly known.

This gap stems from a fundamental supply-chain reality: downstream distributions freeze their kernel baselines for five to ten years to preserve Application Binary Interface (ABI) stability and avoid software regressions~\cite{ruohonen2019tracking}. Upstream code moves rapidly forward, but production operating systems must stay firmly anchored. While prior research has examined dependency lag in user-space registries like npm and PyPI~\cite{alfadel2021empirical, kula2018empirical, pashchenko2020vulnerable}, operating system kernels present a much tougher problem: you cannot simply swap a kernel dependency without risking system boot failures. Yet, past operating system security studies have often relied on small datasets, single-distribution snapshots, or evaluation setups that accidentally leak future data into the past~\cite{zimmermann2010predicting}.

In this paper, we show that downstream security delays are neither random accidents nor simple maintainer oversights. Instead, they are the predictable structural consequence of software divergence between fast-moving upstream development and long-lived enterprise baselines. More importantly, this exposure can be anticipated on Day Zero to help security teams prioritize the fixes that matter most. We organize our study around three core questions:
In \textbf{RQ1 (Predictive Modeling)}, can downstream security exposure be accurately forecasted at disclosure time using strictly pre-remediation signals?
In \textbf{RQ2 (Empirical Patch Lag)}, what is the true real-world duration of downstream exposure windows under supply-chain and public disclosure timelines?
In \textbf{RQ3 (Key Drivers and Determinants)}, which upstream vulnerability metrics, patch traits, and downstream packaging practices govern exposure risk?

Our study delivers five concrete, verifiable contributions:
(1) \textbf{An Audited Security Taxonomy ($D0$--$D6$)}: We formalize a seven-state taxonomy capturing real-world backporting outcomes, validated through an independent double-blind audit ($\kappa = 0.948$) and automated consensus ($\kappa = 0.981$, Section~\ref{sec:background});
(2) \textbf{A Multi-Source Longitudinal Dataset}: We curate a ground-truth dataset cross-referencing NVD, Linux Kernel CVE, Debian Tracker, and Ubuntu Tracker, evaluating all 9,208 common CVEs across six releases (55,248 observations) over two decades without synthetic data (Section~\ref{sec:curation});
(3) \textbf{Empirical Latency Measurement and Survival Analysis}: Across 40,198 ground-truth resolutions, we uncover an empirical median patch lag of 258.8 days (from upstream commit) and 274.6 days (from public disclosure), with a Kaplan-Meier survival probability $\hat{S}(90) = 0.7764$ (Section~\ref{sec:latency});
(4) \textbf{Strict Day-Zero Prospective Exposure Forecasting}: Under an anti-leakage temporal split ($\le$2023 train, $\ge$2024 test; $N_{\text{test}} = 32,536$), our models forecast downstream exposure with an ROC-AUC of 0.8114 (XGBoost) and 75.48\% Balanced Accuracy (Logistic Regression), delivering an operational triage policy that captures 94.3\% of protracted exposures within the top 50\% screening queue (Section~\ref{sec:modeling}); and
(5) \textbf{Structural Feature Attribution and Transferability}: Using held-out permutation importance, we prove that downstream packaging architecture and LTS policy act as primary structural anchors of risk, and validate cross-distribution transferability via Leave-One-Release-Out evaluation (mean ROC-AUC = 0.7549, Section~\ref{sec:importance}).

\section{Ecosystem Background and Downstream Security Taxonomy}
\label{sec:background}

Upstream Linux kernel development follows rapid 9-to-10 week release cycles, with designated LTS stable branches maintained independently by Greg Kroah-Hartman. Downstream distributions handle these updates differently: Debian follows a community rolling model (\textit{sid}, \textit{trixie}) that periodically rebases onto newer stable kernels, alongside a frozen stable model (\textit{bookworm} on Linux 6.1) that applies minimal backports. Ubuntu freezes each LTS suite on a specific kernel (20.04 \textit{Focal} on 5.4, 22.04 \textit{Jammy} on 5.15, 24.04 \textit{Noble} on 6.8), deploying synchronized batch point updates.

\textit{The Packager's Dilemma}: When a security patch lands upstream, packagers face distinct branch divergence realities. Rather than an oversimplified binary patched/unpatched indicator, we formalize a seven-state taxonomy ($D0$--$D6$) capturing nuanced downstream security postures:
\textbf{D0 (Not Affected)}: vulnerable code absent due to version boundaries or disabled config flags;
\textbf{D1 (Vulnerable / Unresolved)}: vulnerable code present and unpatched in production archives;
\textbf{D2 (Clean Upstream Merge)}: upstream patch applied cleanly without code modification;
\textbf{D3 (Adapted Backport)}: maintainers authored non-trivial code adaptations to resolve merge conflicts;
\textbf{D4 (Mitigated / Workaround)}: neutralized through configuration or compiler flags without code patches;
\textbf{D5 (Won't Fix)}: maintainers explicitly decide against patching (e.g., deprecated subsystem); and
\textbf{D6 (End-of-Life / Unsupported)}: release reached end-of-life.

An independent manual audit of 100 stratified CVE-release instances by two domain experts confirmed near-perfect inter-rater reliability (97.0\% agreement, Cohen's $\kappa = 0.948$), and consensus human classifications matched our automated pipeline on 99/100 records ($\kappa = 0.981$). Figure~\ref{fig:taxonomy} depicts the distribution of these security states across all six evaluated releases. In active production suites, states $D4$ (partial fix) and $D5$ (won't fix) account for 0.0\% of records because Debian and Ubuntu classify the kernel as Tier-1 critical infrastructure, mandating formal backports ($D2$/$D3$) for all verified CVEs rather than issuing partial workarounds or unpatched waivers. Similarly, state $D6$ (EOL) is excluded from active evaluations by our Release-Time Validity Protocol.

\section{Longitudinal Multi-Source Dataset Construction}
\label{sec:curation}

To build a reliable ground-truth record of vulnerability propagation, we bring together data from four primary platforms: (1)~\textit{NVD} for disclosure dates and severity ratings (12,176 raw CVEs); (2)~the official \textit{Linux Kernel CVE Repository} for exact Git fixing commits and stable-branch backport tags (9,469 JSON 5.0 records); (3)~the \textit{Debian Security Tracker} for package states in the Debian archive (10,131 package tracking records); and (4)~the \textit{Canonical Ubuntu Security Tracker} for production patch releases across Ubuntu LTS suites (9,210 curated records). Because Canonical maintains a strictly deduplicated kernel repository, their records define the bounding set of our study. Finding the exact intersection across all four sources yields \textbf{9,208 common, verified CVEs} where every milestone is backed by authoritative ground truth. Tracking each vulnerability across six active releases produces \textbf{55,248 release observations}, structured into four relational tables (Table~\ref{tab:schema}).

To ensure our predictive models never peek into the future, we enforce a strict \textbf{Release-Time Validity Protocol}. We remove 508 cases where a vulnerability was disclosed before a target distribution was even released (specifically early-2024 CVEs evaluated against Ubuntu 24.04 Noble, which launched on April 25, 2024). This leaves \textbf{54,740 valid release instances} ($N_{\text{train}} = 22,204$, $N_{\text{test}} = 32,536$). Across these valid instances, we identify \textbf{40,198 ground-truth remediation events} with computable package timestamps (representing a 73.4\% resolution rate).

\section{Empirical Measurement of Downstream Patch Lag (RQ2)}
\label{sec:latency}

\subsection{Dual Latency Metrics and Real-World Timelines}

When a kernel vulnerability is fixed, security teams and attackers operate on very different clocks. Upstream commit authoring and public CVE announcements rarely happen at the same moment. To capture both realities, we formalize and measure two distinct timelines:
\textbf{The Supply-Chain Window} ($\Delta t_{\text{upstream}} = t_{\text{downstream}} - t_{\text{upstream}}$) measures the calendar span from the exact moment an upstream developer commits a fix to the moment downstream distributions upload an updated package. This measures the asymmetric ``one-day'' exploitation window where skilled attackers can inspect public Git commits to craft exploits while downstream servers remain defenseless.
\textbf{The Public Disclosure Window} ($\Delta t_{\text{disclosure}} = t_{\text{downstream}} - t_{\text{disclosure}}$) tracks the duration between formal NVD publication and downstream package deployment, representing the window during which security officers and compliance auditors are actively aware of the threat.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.88\textwidth,height=3.4cm,keepaspectratio]{figures/fig1_survival_remediation_latency.pdf}
\caption{Downstream remediation dynamics: (Left) Empirical cumulative distribution of patch delay across 40,198 resolved vulnerabilities; (Right) Kaplan-Meier survival curves comparing patch lag between Debian and Ubuntu.}
\label{fig:survival}
\end{figure}

Measuring these timelines across 40,198 confirmed fixes reveals an eye-opening reality: downstream patching is far slower than traditional compliance windows assume. Under the \textbf{Supply-Chain Window} ($\Delta t_{\text{upstream}}$), fixes take an average of \textbf{306.60 days} ($\approx 10.1$ months) and a median of \textbf{258.77 days} ($\approx 8.5$ months) to reach users. Fully \textbf{69.3\%} of all resolved vulnerabilities take longer than 90 days to patch, and \textbf{21.4\%} remain unpatched for over a full calendar year. Under the \textbf{Public Disclosure Window} ($\Delta t_{\text{disclosure}}$), 93.1\% of instances ($N = 37,415$) were patched on or after disclosure, with a median exposure window of \textbf{274.59 days} (mean 327.02 days, 74.2\% $>90$ days, and 40.2\% $>365$ days). A small fraction (6.9\%, $N = 2,783$) appeared to be resolved before formal disclosure; this reflects an administrative artifact rather than psychic maintainers, caused when the Linux kernel security team bulk-assigned historical CVE IDs in early 2024 to commits merged years prior.

\subsection{Survival Analysis: Debian vs. Ubuntu}

Because some vulnerabilities remain unpatched at the time of data collection, simply taking the average over resolved cases would underestimate the true risk. To handle this properly, we apply non-parametric \textbf{Kaplan-Meier survival analysis}:
\begin{equation}
\hat{S}(t) = \prod_{t_i \le t} \left(1 - \frac{d_i}{n_i}\right)
\end{equation}
where $t_i$ represents distinct event times, $d_i$ is the number of packages patched at $t_i$, and $n_i$ represents vulnerable instances still awaiting a fix immediately before $t_i$. Computing confidence intervals with Greenwood's formula, the empirical probability that an affected system remains unpatched is $\hat{S}(30) = 0.8735$ [95\% CI: 0.8707, 0.8763], $\hat{S}(90) = 0.7764$ [95\% CI: 0.7729, 0.7799], $\hat{S}(180) = 0.7106$ [95\% CI: 0.7068, 0.7144], and $\hat{S}(365) = 0.5467$ [95\% CI: 0.5425, 0.5508]. In plain terms, three out of four vulnerable systems remain unpatched three months after disclosure, and over half are still unpatched after an entire year.

As illustrated in Figure~\ref{fig:survival}, the survival curves mirror the distinct engineering cultures of the two distributions. Debian rolling releases display steep vertical drops whenever the distribution rebases onto a newer kernel, wiping out large backlogs of vulnerabilities in a single sweep; its frozen stable releases, by contrast, plateau as backports taper off. Ubuntu displays steady, stair-stepped declines corresponding to its scheduled point-update kernel builds.

\section{Predictive Modeling of Downstream Security Exposure (RQ1)}
\label{sec:modeling}

\subsection{Formulation and Out-of-Time Protocol}

To help security teams get ahead of this lag, we cast downstream exposure prediction as a supervised binary classification problem. For any given vulnerability and target release, our model predicts $y \in \{0, 1\}$ directly from distribution tracker ground truth:
\textbf{Exposed ($y = 1$)}: The target release is actively affected and unpatched in production archives ($D1\_vulnerable$, including statuses \texttt{needed}, \texttt{unfixed}, \texttt{open}, and \texttt{deferred}) or partially mitigated ($D4\_partial\_fix$).
\textbf{Protected ($y = 0$)}: The system is secure---either because vulnerable code was never included in that release ($D0\_not\_affected$, statuses \texttt{not-affected}, \texttt{DNE}), or because a patch has been integrated ($D2\_fixed\_equivalent$, $D3\_modified\_fix$, or $D5\_config\_unreachable$).

\textit{Reconciling Latency and Classification}: While survival analysis (Section~\ref{sec:latency}) measures the velocity of completed fixes ($N = 40,198$), our classifier evaluates all active and pending packages at a snapshot, labeling unresolved instances as exposed ($y = 1$). This explains why dataset positive rates (28.21\% in train, 26.05\% in test) differ from the 90-day survival probability $\hat{S}(90) = 0.7764$: classification assesses whether a server is currently vulnerable versus safe, whereas survival curves track how quickly resolved patches were delivered.

To mirror real-world deployment, we enforce a strict \textbf{anti-leakage temporal split} with release-time validity, training exclusively on vulnerabilities disclosed up to 2023 ($N_{\text{train}} = 22,204$) and evaluating prospectively on unseen bugs from 2024--2025 ($N_{\text{test}} = 32,536$). All encoders are fit strictly on training data. Our feature representation relies solely on information visible on Day Zero, spanning 52 generalizable attributes (46 when release dummies are omitted for cross-release transfer): (1)~vulnerability traits (35 features: CVSS base score, attack vector, attack complexity, 15 kernel subsystems, and 10 collapsed CWE classes such as out-of-bounds access, use-after-free, buffer overflows, and race conditions, grouped from $>65$ raw NVD identifiers); (2)~upstream patch complexity (7 features: lines added/deleted, churn, hunk count, modified file count, and commit message length); and (3)~downstream architecture (10 features: distribution family, release indicators, base kernel versions, and LTS status). No post-disclosure features (such as Git stable backport counts) are included.

\section{Feature Attribution, Cross-Release Transfer, and Boundary Conditions (RQ3)}
\label{sec:importance}

\begin{figure}[htbp]
\centering
\includegraphics[width=0.80\textwidth,height=3.2cm,keepaspectratio]{figures/fig3_feature_importance.pdf}
\caption{Prospective permutation feature importance evaluated on the out-of-time test set ($N_{\text{test}} = 32,536$), reporting the reduction in prospective ROC-AUC when each feature is permuted (zero post-disclosure features, release codename dummies excluded).}
\label{fig:importance}

To understand what drives exposure risk without falling into Gini split biases, Figure~\ref{fig:importance} reports \textbf{Permutation Feature Importance} measured on the held-out test set ($N_{\text{test}} = 32,536$). Shuffling feature values reveals a two-tier hierarchy:

\textit{1. Primary Structural Determinants}: Downstream packaging policies and release architectures establish baseline exposure risk. Permuting the distribution ecosystem feature (\texttt{downstream\_debian} vs. \texttt{ubuntu}) causes a \textbf{0.2527 drop in ROC-AUC} (100.0\% relative importance). This prominence reflects governance mechanics rather than label memorization: Debian rolling branches rebase kernels periodically (clearing exposure backlogs in large batches), whereas Ubuntu LTS enforces synchronized point-update batching on pinned branches. When release dummies are stripped to evaluate generalizability (Figure~\ref{fig:importance}), structural features---specifically LTS status (\texttt{is\_lts}, causing a \textbf{0.0441} drop in ROC-AUC, 17.5\% relative importance) and base kernel versions---remain the primary anchors of exposure risk.

\textit{2. Secondary Modulators}: Within a given distribution architecture, upstream vulnerability traits and patch complexity modulate individual remediation speed. External scrutiny (\texttt{reference\_count}) ranks as the leading secondary predictor (+0.0533 AUC drop, 21.1\% relative importance), as high-visibility bugs command urgent triage. Upstream patch complexity provides additional discriminative signal: code expansion (\texttt{loc\_added}, +0.0006 AUC), patch hunk count (\texttt{patch\_hunks}, +0.0004 AUC), modified file count (\texttt{files\_changed\_count}, +0.0004 AUC), and commit message length (\texttt{commit\_message\_length}, +0.0003 AUC). Large diffs frequently fail automated cherry-picking against divergent LTS trees, requiring manual rewrites. Subsystems such as memory management (\texttt{affected\_component\_mm}, +0.0010 AUC) and \texttt{bluetooth} (+0.0001 AUC) also present elevated friction due to complex concurrency and hardware testing requirements.

Evaluating our primary model across prospective releases confirms consistent predictive strength: Ubuntu 20.04 LTS (\textit{Focal}) achieves ROC-AUC = \textbf{0.8214} (PR-AUC = 0.9366); Ubuntu 22.04 LTS (\textit{Jammy}) attains ROC-AUC = \textbf{0.8401} (PR-AUC = 0.8959); Ubuntu 24.04 LTS (\textit{Noble}) achieves ROC-AUC = \textbf{0.7998} (PR-AUC = 0.4245); Debian 12 (\textit{Bookworm}) attains ROC-AUC = \textbf{0.7035}; and Debian 13 (\textit{Trixie}) attains ROC-AUC = \textbf{0.6257}. Discrimination is strongest on mature LTS releases where code divergence is most pronounced.

Under \textbf{Leave-One-Release-Out (LORO) Cross-Validation} (training on four releases and evaluating on an unseen fifth release without release dummies), models transfer strongly across mature LTS suites: held-out Ubuntu 22.04 (\textit{Jammy}) achieves ROC-AUC = \textbf{0.8667} (PR-AUC = 0.8664); held-out Ubuntu 20.04 (\textit{Focal}) attains ROC-AUC = \textbf{0.7968}; held-out Debian 13 (\textit{Trixie}) achieves ROC-AUC = \textbf{0.7762}; and held-out Debian 12 (\textit{Bookworm}) achieves ROC-AUC = \textbf{0.7523}.

On held-out Ubuntu 24.04 (\textit{Noble}), the transfer model attains an ROC-AUC of \textbf{0.5827} (PR-AUC = 0.5481), highlighting an honest boundary condition: Noble launched in late April 2024 running Linux 6.8, in close proximity to upstream mainline during our snapshot. Because brand-new releases have not yet diverged significantly and have not accumulated mature backport backlogs, models evaluated out-of-release encounter a cold-start setting. Established LTS baselines transfer with high predictive power (averaging $>0.80$ ROC-AUC), while newly deployed releases benefit from brief calibration as packaging cadences stabilize. Across all held-out releases, the model maintains an average LORO ROC-AUC of \textbf{0.7549}.

\section{Practical Implications and Threats to Validity}
\label{sec:guidelines}

Our findings offer practical guidance across the software supply chain. For \textbf{downstream packagers}, waiting for public CVE advisories leaves systems exposed for hundreds of days; maintainers should deploy automated day-zero triage to flag difficult backports the day upstream commits land, leveraging live-patching tools (\texttt{kpatch}, \texttt{livepatch}) to deliver urgent fixes without waiting for monolithic rebuild cycles. For \textbf{upstream maintainers}, backport friction decreases substantially when developers annotate patches with \texttt{Cc: stable@vger.kernel.org} and document tricky dependencies. For \textbf{enterprise security teams}, vulnerability scanners must audit installed package versions rather than upstream Git commit dates: upstream fixes provide zero protection until downstream packages are rebuilt and deployed.

We address four threats to validity:
(1)~\textit{Construct}: All downstream states and timestamps were ingested directly from official Debian and Ubuntu trackers and verified against package changelogs.
(2)~\textit{Internal}: We enforced strict out-of-time splits ($\le$2023 train, $\ge$2024 test), pruned pre-release anachronisms, and treated unpatched flaws as right-censored cases using Kaplan-Meier survival curves.
(3)~\textit{External}: Debian and Ubuntu form the foundation for hundreds of enterprise distributions, cloud images, and container operating systems (e.g., Linux Mint, Pop!\_OS), which inherit identical delays.
(4)~\textit{Conclusion}: Tracking 9,208 common CVEs across 55,248 release observations provides high statistical power across all reported benchmarks.

\section{Related Work}
\label{sec:related}

\textit{Software Supply Chains and Dependency Lag}: Studies by Kula et al.~\cite{kula2018empirical} and Alfadel et al.~\cite{alfadel2021empirical} demonstrated that developers frequently delay updating libraries in user-space registries (npm, PyPI, Maven) to avoid breaking software. Pashchenko et al.~\cite{pashchenko2020vulnerable} further showed that counting vulnerable libraries without checking call-path reachability overstates operational risk. Our work extends empirical supply-chain analysis to operating system kernels, where ABI stability must be maintained across multi-year LTS cycles~\cite{decoster2022measuring}.

\textit{Operating System Vulnerability Lifecycles}: Longitudinal analyses by Ruohonen et al.~\cite{ruohonen2018empirical, ruohonen2019tracking} traced vulnerability lifetimes across thousands of Debian packages. In parallel, Wang et al.~\cite{wang2020empirical} investigated how security bugs propagate across upstream Linux kernel branches. DownstreamSec synthesizes these lines of inquiry: by triangulating 9,208 common CVEs across upstream Git, NVD, Debian, and Ubuntu, we formalize an audited seven-state taxonomy ($\kappa = 0.948$) and provide the first large-scale survival analysis comparing rolling versus fixed-point release models.

\textit{Predictive Vulnerability Modeling}: Machine learning has long been applied to software security, including component vulnerability prediction~\cite{scandariato2014predicting}, exploitability forecasting~\cite{freitas2021predicting}, and patch duration analysis~\cite{saha2018understanding}. However, as Zimmermann et al.~\cite{zimmermann2010predicting} warned, software prediction models frequently suffer from subtle temporal and spatial leakage. Our study heeds this lesson: by enforcing prospective out-of-time evaluation ($\le$2023 train, $\ge$2024 test), removing pre-release anachronisms, and conducting Leave-One-Release-Out validation, DownstreamSec provides an ecologically valid benchmark for downstream security forecasting.

\section{Conclusion and Future Horizons}
\label{sec:conclusion}

Downstream vulnerability exposure in open-source operating systems is driven by structural packaging dynamics rather than upstream code churn alone. Across 55,248 release observations spanning Debian and Ubuntu over two decades, downstream servers endure a median patch delay of 258.8 days after an upstream fix is committed, with 77.6\% remaining exposed past 90 days. Furthermore, this exposure is predictable on Day Zero: pre-remediation signals forecast downstream exposure with an ROC-AUC of 0.8114, enabling an operational triage policy that catches 94.3\% of protracted exposures while cutting maintainer review queues in half.

Closing the upstream-to-downstream gap requires two systemic shifts: (1)~automated semantic backport tools that leverage Day-Zero triage signals to generate conflict-free candidate patches before human review; and (2)~broader adoption of kernel live-patching to decouple urgent fixes from monolithic rebuild cycles.
All raw datasets, processed tables, feature matrices, benchmark models, and reproduction scripts are openly available at: \url{https://github.com/kh0kamoni/DownStream}.
